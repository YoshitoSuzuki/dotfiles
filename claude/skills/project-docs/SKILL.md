# プロジェクトドキュメント整備スキル

## 目的

**時間が経って何もかも忘れた未来の自分が、これだけ読めば再開できる**状態を作る。Claudeのためのメモ（CLAUDE.md）とは別物で、docs/ は人間が読むためのもの。

## 標準構成

プロジェクトルートに `docs/` を作り、以下を必要に応じて用意する（全部必須ではない。そのプロジェクトに意味のあるものだけ）：

| ファイル | 内容 |
|---|---|
| `docs/overview.md` | サービス・アプリの概要：何のために作ったか、主要機能、誰が使うか、公開場所（URL/ストアリンク）、関連リポジトリ |
| `docs/architecture.md` | 使用技術と仕組み：言語/フレームワーク、全体構成図（テキストで可）、主要ファイルの役割、外部サービス・API、データの流れ、秘密情報（.env）に何が入るか（**値は書かない**） |
| `docs/build.md` | 環境構築とビルド方法：必要なツールとバージョン、セットアップ手順、ビルドコマンド、よくあるビルドエラーと対処 |
| `docs/test.md` | テスト・動作確認の方法：テストの実行コマンド、手動での動作確認手順（何をどの順で触れば正常と言えるか）、確認用のアカウント・端末の情報の在り処 |
| `docs/release.md` | 更新・リリース手順：バージョンアップからユーザーに届くまでの全手順（ビルド→配置→デプロイ/申請）、配布物の置き場所、ロールバック方法 |
| `docs/history.md` | 開発の経緯：時系列で「いつ・何を・なぜそうしたか」。特に**後から見て不思議に思いそうな設計判断の理由**を残す |

## 書き方のルール

- **読者は「全部忘れた数年後の自分」**。前提知識を省略しない。専門用語には一言説明を付ける
- コマンドは説明だけでなく**そのままコピペで動く形**で書く（実際のパス・実際のオプション込み）
- 書く前に必ずコードと設定を読んで実態から書く。**推測で書かない**。可能ならビルドコマンド等は実行して動くことを確認してから記載する
- 手順は番号付きリストで、各ステップに「成功するとこうなる」を添える
- 日付を入れる（`history.md` は必須、他も「最終更新: YYYY-MM-DD」を先頭に）
- 秘密情報（パスワード、APIキー、トークン）は絶対に書かない。「.env の XXX に設定」という形で在り処だけ示す

## 作成手順

1. プロジェクトを調査する：README、CLAUDE.md、設定ファイル（pubspec.yaml / project.pbxproj / package.json 等）、git log、ディレクトリ構成
2. git log から開発の流れを復元して `history.md` の下書きにする
3. 上の表から**そのプロジェクトに必要なファイルだけ**選んで書く（静的サイトに test.md は不要、など）
4. わからないこと（作った動機、手動テストの勘所、リリースの実績手順など）は**推測せずユーザーに質問**してから書く
5. 書き終えたら各ファイルの要約を報告し、ユーザーに一読を促す

## 更新の運用

- 既に docs/ があるプロジェクトで**ビルド方法・リリース手順・構成に関わる変更**をしたら、作業の締めに該当ドキュメントの更新まで行う（これはこのスキルの発動を待たず常に意識する）
- 大きめの機能追加・仕様変更をしたら `history.md` に1行追記を提案する
- 古くなった記述を見つけたら勝手に消さず、修正案を添えてユーザーに確認する
