# CLAUDE.md（共通）

どのマシンの Claude Code でも共通して適用する指示。dotfiles（public リポジトリ）で管理し、
各マシンの `~/.claude/CLAUDE.md` から `@~/.claude/dotfiles/CLAUDE.md` で読み込んでいる。
マシン固有・個人に関わる指示は各マシンの `~/.claude/CLAUDE.md` に書く。

## マシン・プロジェクトごとの決まりとの関係

- 作業するプロジェクトに CLAUDE.md・docs/・独自のブランチ運用やコミット規約があれば、そちらを優先する
  （会社のリポジトリでは特に、ここに書いたブランチ運用・コミットメッセージの形式を押し付けない）
- 各マシンの `~/.claude/CLAUDE.md` に書いた指示も、ここより優先する

## 言語

- 日本語で質問，askした場合は特に指定のない限り日本語で返答してください。
- 指定のない限りタメ口はやめてください．
- 会話が長くなっても、ツールの出力やスキルの説明が英語でも、返答の言語は変えない（2026-10-05 に長い会話の途中から英語で返答してしまった）。
  日本語のメッセージには `~/.claude/hooks/japanese-reply.py`（UserPromptSubmit フック）が毎回「日本語で返答」の注意を差し込む

## 個人情報の扱い

- **個人情報（メールアドレス・住所・電話番号・生年月日・アカウント情報など）を、許可なく公開したり外部に出したりしない**
- 公開リポジトリへのコミット・Webサイトへの掲載・外部サービスへの送信・公開URLを持つページの作成などで
  個人情報が含まれる可能性があるときは、実行前に中身を確認し、含まれていれば必ずユーザーに許可を取る
- コード・設定・コミットメッセージ・ログ・ドキュメントにも、必要のない個人情報を書き込まない
- 会社のマシンでは、会社の業務に関する情報（コード・資料・社内の名前・URL・顧客情報など）も
  個人情報と同じく扱い、公開リポジトリ（dotfiles を含む）や外部サービスに出さない

## コーディング方針

- 既存のコードスタイル・命名規則に合わせる
- 要求されていないリファクタリングや抽象化、コメント追加は行わない
- 不要な防御的コーディング（起こり得ないケースのエラーハンドリング等）は書かない
- git のコミットメッセージは英語小文字の短文（例: `add tmu-app page`, `fix header layout on mobile`）
- **公開するページのURLにファイル名を出さない**。`~~/share.php` や `~~/about.html` ではなく
  `~~/share/` `~~/about/` の形にする（ページごとにディレクトリを切って `index.php` /
  `index.html` を置く）。新規ページはこの形で作り、既存を移したときは旧URLから
  301リダイレクトを残す。ページの深さが変わるので、リンクやCSS/JSの参照は
  相対パスではなくルート相対で組み立てること

## ブランチ運用（全プロジェクト共通）

**どのプロジェクトでも、以下のブランチ運用に従う。**
main（master）で直接作業しない。

### 戦略: Git-flow（全プロジェクト共通）

**Webサイトも含め、すべてのプロジェクトで Git-flow を使う。**
`main` から直接作業ブランチを切らない。

1. `main` から `develop` を切る（まだ無いプロジェクトなら最初に作る）
2. `develop` からさらに作業ブランチを切って作業する
3. 作業ブランチ → `develop` にマージ
4. 公開・リリース時に `develop` → `main` にマージし、そこからデプロイする

長期に残すブランチは `main` と `develop` の2つ。

### ブランチ命名規則

形式: `<type>/<short-kebab-case-description>`

type は `feature`（機能追加）/ `fix`（不具合修正）/ `hotfix`（公開中の緊急修正）/
`chore`（設定・整理）/ `refactor`（挙動を変えない書き換え）/ `docs`（ドキュメント）/
`test`（テスト）の7種類のみ。リリース確定版を残す `release/v.x.y.z` だけは例外
（下の「リリースブランチ」を参照）。

説明部分は **2〜4単語程度**、すべて小文字、単語はハイフン区切り。
文章的な説明（動詞を並べた長い説明、`and` で複数の内容をつなぐ）は禁止。

- 良い例: `feature/izu-trip-page`
- 悪い例: `feature/add-a-new-page-for-izu-trip-and-fix-broken-links`

### 作業フロー

1. `develop` を最新化する（無ければ `main` から作る:
   `git switch main && git pull && git switch -c develop`）
2. `develop` から作業ブランチを切る: `git switch -c <type>/<short-kebab-case-description>`
3. 作業する（生成物のビルドが要るプロジェクトはビルドまで済ませる）
4. コミット（メッセージは英語小文字の短文）
5. `git push -u origin <branch>`
6. `gh pr create --base develop` で PR を作る
7. `develop` にマージ（squash merge を基本にし、1つの作業＝`develop` の1コミットにする）
8. **`develop` で動作確認する**（アプリならシミュレータ・実機で変更した画面を実際に操作する、
   サイトならローカルやプレビューで表示を確かめる）。ビルドが通っただけで確認済みとしない
9. 問題が無ければ、公開・リリースするタイミングで `develop` → `main` の PR を出してマージする。
   **この段階は必ず事前にユーザーへ確認する**。動作確認前に `main` へのマージや公開をしない
10. マージした `main` と同じ内容を `release/v.x.y.z` にも入れて push する
    （下の「リリースブランチ」）
11. **`main` からビルド・アーカイブ・デプロイ・ストア送信を行う**

### リリースブランチ（確定版を残す）

**リリースのたびに、その版のコードを `release/v.x.y.z` ブランチとして残す。**
あとから「どのバージョンで何を公開したか」を正確にたどれるようにするため。

- ブランチ名は `release/v.<major>.<minor>.<patch>`（例: `release/v.2.1.0`）
- 手順は「`develop` で動作確認 → `develop` を `main` にマージ → その `main` と同じ内容を
  `release/v.x.y.z` にも入れて push」。**最新の `release/v.x.y.z` は `main` と同じ状態**になる
  （`git switch -c release/v.2.1.0 main && git push -u origin release/v.2.1.0`）
- アプリの場合、**バージョン番号（`MARKETING_VERSION` / ビルド番号）を上げたコミットを
  含んだ状態**にしてからリリースする。番号を上げずに出さない
- **バージョン x.y.z の x（メジャー）や y（マイナー）を自己判断で上げない**。上げるのは基本的に z（パッチ）だけにし、
  x・y を上げたほうがよさそうなときは、上げる前に必ずユーザーに確認する。機能を足しただけで y をすぐ上げない
  （2026-10-06 に TMU を 1.3.0 → 1.4.0 にして「そんなにすぐ y を上げないでほしい」と言われ、1.3.1 に直した）。
  リリースブランチに限らず、バージョン番号を持つものすべてに適用する。プロジェクトの CLAUDE.md や docs/ に
  別の決まりがある場合はそちらに従う
- 過去の `release/v.x.y.z` ブランチは**消さない**。公開中の版を直すときは `hotfix/` で
  作業し、`develop`・`main` に入れてから新しい `release/v.x.y.z` を作る
- デプロイ・ストア送信は `main` から行う

### マージ後のブランチ削除

- PR をマージしたら、**作業ブランチはリモート・ローカルとも削除する**
  （`gh pr merge --squash --delete-branch` → `git switch develop && git pull && git branch -d <branch>`）
- 削除しないのは `main` / `develop` / `release/v.x.y.z` のみ
  （`develop` は `main` にマージ後も残す）

### 新しいプロジェクトに適用するとき

- そのプロジェクトの CLAUDE.md にこのルール（Git-flow・命名・フロー・削除）を書く
- リポジトリを作ったら最初に `main` から `develop` を切っておく
- **リポジトリの中身がそのまま公開される構成のプロジェクトでは、CLAUDE.md を
  コミットせず `.gitignore` に入れる**（例: yoshito.me はリポジトリが丸ごと
  `/var/www/html/` にコピーされるため、コミットすると CLAUDE.md が Web で読めてしまう）

## 作業の進め方

- 新しく作成するディレクトリの名前はアルファベットもしくは数字にする（docs, src, notes のような形式）。日本語のディレクトリ名は使わない
- 破壊的な操作（force push、reset --hard、ファイル削除など）を行う前には必ず確認を取る
- **プロジェクト・ディレクトリ・ファイルなどを元に戻せない形で削除するときは、どんな場合でも必ず事前に許可を取る**。
  auto mode や「進めて」と言われている途中でも省略しない。消す対象を実際に見て、何を消すのかを示してから聞く
- **ユーザーの実データ（実機のカレンダー・リマインダー・写真・連絡先など）を、動作確認のために書き換えない**。実機での確認は読み取りだけにし、書き込みを伴う確認はシミュレータのサンプルで行う。必要なら事前に許可を取る（2026-10-03 にリマインダーの期限を勝手に書き換えて「絶対やめて」と言われた）
- 大きめのタスクは着手前に方針を簡潔に説明する
- ファイルの編集など作業を開始する前に、作業用のブランチに切り替える（新規作成する）。ブランチ名と作業フローは上の「ブランチ運用（全プロジェクト共通）」に従う
- プロジェクトに `CLAUDE.md` がある場合（例: TMUアプリ）は、作業前に必ずそれを読む
- **作業前に既存の記録をすべて参照する**: 対象プロジェクトの `docs/`（特に release.md）・プロジェクトCLAUDE.md・git log・メモリを読み、アプリやサービスの仕組みと影響範囲を理解してから着手する。複数リポジトリ/プラットフォームにまたがるプロジェクト（例: TMUはSwift版とFlutter版が1つのリリースタグを共有）では、直接触らないリポジトリの docs/ にも制約が書かれていることがあるので必ず確認する
- **作業後は記録を残す**: docs/history.md への追記、手順・構成が変わったら docs/ 該当ファイルの更新、汎用的な教訓はメモリへの保存まで行ってから作業完了とする
- リリース・公開などやり直しの難しい操作は、着手前に方針を説明して確認を取る
- 何かを作り終えたら、ユーザーが自分で確認できる方法（`open` するファイル、URL、実行コマンド）を最後に必ず示す

## ナレッジベース（知識の保存と参照）

毎回同じ説明を繰り返さなくて済むよう、セッションで得た知識を `~/.claude/knowledge/` に蓄積する。`INDEX.md` が索引（1行=1項目）。

- **参照**: 作業を始める前に `~/.claude/knowledge/INDEX.md` を読み、作業内容に関係しそうな項目があれば該当ファイルを読んでから着手する
- **保存**: 作業中に得た再利用可能な知識（環境の癖・ハマりどころと解決法・確立した手順・ユーザーの好みや決定事項）は、作業の締めに保存する。1トピック=1ファイル、ファイル名は英数字の kebab-case、冒頭に `- 更新日: YYYY-MM-DD` を入れ、INDEX.md にも1行追記する
- **重複回避**: 既存項目と重なる内容は新規ファイルを作らず既存ファイルを更新する。間違いだと判明した知識は修正または削除する
- **保存しないもの**: リポジトリ内の docs/ や CLAUDE.md にすでに書いてあること、その会話限りの一時的な情報
- ユーザーが「これ覚えといて」と言ったら、指定がなければここに保存する
- **共有ナレッジ**: どのマシンでも使える汎用の知識は `~/.claude/dotfiles/knowledge/`（dotfiles で公開）にある。
  作業前に `~/.claude/knowledge/INDEX.md` とあわせてこちらの `INDEX.md` も読む
- 新しい知識の保存先は `~/.claude/knowledge/`（そのマシンだけのもの）。dotfiles 側に入れるのは
  ユーザーが明示したときだけにする（public なので、個人情報・会社の情報・特定のマシンの環境に依存する内容は入れない）
- **会社のマシンでは dotfiles を編集・コミットしない**（pull だけにする。会社の git 設定のメールアドレスで
  public リポジトリにコミットしてしまうのを防ぐため）

## 文章表現

- **「ハマる」「ハマりどころ」は使わない**（チャットの返答・ドキュメント・コメントすべて）。
  同じ言い回しを何度も繰り返されると読んでいて不快なため。
  代わりに「間違えやすい点」「失敗しやすい点」「注意点」など、内容に合った言葉を選ぶ
- 特定の言い回しを機械的に繰り返さない。同じ意味でも文脈に応じて言葉を変える
- **目的語を必要とする動詞を、目的語なし・曖昧な意味のまま使わない**。
  「形にする」「回す」「持っていく」「吸収する」「見直す」「対応する」などは、
  何を・どうするのかを具体的に書く。これはチャットの返答・ドキュメント・
  提出書類（履歴書やESの文章を含む）すべてに適用する
  - 悪い例:「手を動かして形にすることで貢献したい」「次の版を出すところまで回している」
  - 良い例:「検証用の試作を実装する作業を引き受けたい」
    「審査で受けた指摘に対応して修正版を提出し、公開後は不具合の報告を受けて次のバージョンを出している」

## ルールの記録

- 作業途中でユーザーが「今後のClaude利用全般で共通化できそうなルール・決まり・お願い」をした場合は、そのつど自動的にこの `~/.claude/CLAUDE.md` に追記すること
- 追記先は基本的にそのマシンの `~/.claude/CLAUDE.md`。どのマシンでも通用し、公開してよい汎用ルールだけを
  dotfiles の共通ファイルに書く（迷ったらマシン側）
